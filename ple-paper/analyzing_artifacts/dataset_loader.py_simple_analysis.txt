Below is a detailed logic analysis for the dataset_loader.py module. This module’s primary responsibility is to read in the raw dataset (using pandas), apply all necessary preprocessing (for both numerical and categorical features), and then split the data into training, validation, and test sets. The following points outline in depth how we plan to implement this in accordance with the paper’s methodology, the overall plan, the design’s data structures/interfaces, and the configuration provided in config.yaml.

────────────────────────────────────────────
1. Overall Responsibilities

• Read the dataset (assumed to be in CSV or a similar format) using pandas.
• Identify numerical and categorical features. (If the config specifies or if types can be inferred automatically.)
• Preprocess features:
  – For numerical features: If the config flag “apply_preprocessing” is true and the transformer is set to “QuantileTransformer,” then apply scikit-learn’s QuantileTransformer. This not only scales but also maps data to a target distribution (typically uniform in [0, 1]). Note that while PLE embeddings are shift–scale invariant, the config currently enforces the transformer unless further logic is added later.
  – For categorical features: Apply one-hot encoding—using either pandas’ get_dummies or scikit-learn’s OneHotEncoder—to convert these features into a binary indicator format.
• Split the dataset into three disjoint sets: training, validation, and test. This will be done using scikit-learn’s train_test_split (possibly in two stages) to ensure reproducibility
  – Use the “seed” value from the configuration (e.g., 42) to set random_state in the splitting functions.
  – Choose appropriate split ratios (e.g., 70% train, 15% validation, 15% test) unless specific ratios are provided.
• Package the three splits into a DataBundle data structure that contains attributes for train, val, and test.

────────────────────────────────────────────
2. Class Structure and DataFlow

A. DataBundle
 • A simple data container (class DataBundle) that holds:
  – train data (features and labels)
  – validation data (features and labels)
  – test data (features and labels)
 • This structure is returned from the load_data() method of DatasetLoader and is passed along to downstream modules (Trainer and Evaluator).

B. DatasetLoader Class
 • __init__(self, config: dict)
  – The constructor will take in a configuration dictionary (loaded by config.py) that includes:
   ◦ data_preprocessing parameters:
    ▪ numerical.transformer (should be “QuantileTransformer” per config.yaml)
    ▪ apply_preprocessing flag
    ▪ categorical.encoding (set to “one-hot”)
   – Possibly the dataset’s file path, or other dataset-specific settings if provided by the config.
 • load_data(self) -> DataBundle
  – This is the primary method to:
   1. Load the dataset from disk (using pandas.read_csv or a similar function).
   2. Separate features (X) from the target/label (y). The target column might be specified in the config or inferred automatically.
   3. Detect or determine which columns are numerical and which are categorical:
    ◦ For numerical features: these will later be sent through scaling (QuantileTransformer) if preprocessing is enabled.
    ◦ For categorical features: apply one-hot encoding.
   4. Preprocessing Steps:
    – If config["data_preprocessing"]["apply_preprocessing"] is true:
     ○ For numerical features:
      § Instantiate a QuantileTransformer from scikit-learn (using the default parameters or any parameters defined in the config).
      § Fit the transformer on the training portion of the data (to avoid data leakage) and transform all splits consistently.
    – For categorical features:
     ○ Apply one-hot encoding (e.g., via pandas.get_dummies or a OneHotEncoder), ensuring that the same transformation is applied to training, validation, and test sets.
   5. Data Splitting:
    – Use scikit-learn’s train_test_split in a two-step process:
     ○ First, split the full dataset into a “train” set and a “temp” set (where temp is later split into validation and test).
     ○ Then split the “temp” set into validation and test sets (for example, using an equal split or any prescribed ratio).
    – Ensure that the random_state parameter is set to the value in the configuration seed (e.g., 42) to ensure reproducibility.
    – If the task is classification, consider stratifying based on the target labels.
   6. Package the resulting splits into a DataBundle instance and return it.

────────────────────────────────────────────
3. Key Points and Decision Details

• Preprocessing:
 – Numerical: The config explicitly states “QuantileTransformer” under data_preprocessing.numerical so the QuantileTransformer from scikit-learn will be instantiated and applied. (Remember that while PLE representations are naturally in [0, 1], for consistency across models we will apply the QuantileTransformer as per config. Future extensions may allow conditionally skipping this step.)
 – Categorical: Since the config indicates one-hot encoding, use a standard one-hot implementation. The choice between pandas.get_dummies or scikit-learn’s OneHotEncoder is flexible but should remain consistent across runs.

• Data Splitting:
 – Implement a two-stage split to first carve out a training set and then subdivide the remaining data into validation and test sets.
 – The exact ratios might be hardcoded (for instance, 70/15/15) in the absence of explicit configuration, but this should be documented.
 – Use the provided “seed” from config.yaml to ensure that the randomness is controlled.

• Handling Dataset Formats:
 – Although the paper mentions several public datasets, this module should be kept generic. The DatasetLoader might rely on a configuration parameter (or additional arguments) that specify the filename or the columns that represent numerical or categorical data.
 – If such metadata is not provided, the loader can infer data types from the pandas DataFrame (for example, using DataFrame.select_dtypes).

• Error Handling and Logging:
 – Include basic checks (e.g., file exists, non-empty data, proper separation of features and labels).
 – Log dataset dimensions both before and after preprocessing and splitting to help troubleshoot issues.
 – If a column contains unexpected values (e.g., missing values), the module should either handle them (through imputation) or raise an informative exception.

• Reproducibility:
 – Use the random_state parameter in all functions that incorporate randomness (e.g., train_test_split).
 – While global seed setting might occur in a utility module, ensure that dataset splitting respects the provided config seed.

────────────────────────────────────────────
4. Summary of the Data Flow

1. The DatasetLoader is instantiated with the config dictionary.
2. Inside load_data():
 – The raw dataset is read using pandas.
 – The features (X) and label (y) are separated.
 – Columns are split into numerical and categorical features.
 – Numerical features are transformed via QuantileTransformer (if apply_preprocessing is true).
 – Categorical features are encoded using one-hot encoding.
 – The full data is split into training, validation, and test sets in a reproducible fashion using the config seed.
3. A DataBundle instance is constructed holding the three splits and returned.
4. This DataBundle is then used by training and evaluation modules downstream.

────────────────────────────────────────────
5. Integration Considerations

• The module should strictly use the configuration values from config.yaml (e.g., batch_size is not used here directly but the seed and preprocessing type are crucial).
• The design does not change any interfaces: the DataBundle is a plain data container, and the DatasetLoader only returns this object via its load_data method.
• Any utility functions (such as for logging or additional preprocessing) should be placed in utils.py and imported here for code clarity.

By following this detailed logic, the dataset_loader.py module can be implemented to reliably feed preprocessed, well-split data into our training pipeline, ensuring that the experimental setup aligns with both the paper’s methodology and our overall design.
