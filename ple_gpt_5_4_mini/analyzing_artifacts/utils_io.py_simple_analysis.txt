# Logic Analysis: `utils/io.py`

This module is the configuration and persistence hub for the entire reproduction pipeline. It must support:

- loading the experiment configuration from `config.yaml`
- serializing results, tuned hyperparameters, predictions, and checkpoints metadata
- deserializing previously saved artifacts
- providing a typed, reproducible config object that downstream modules can rely on

It is a foundational utility because every experiment path in the paper depends on consistent configuration handling.

---

## 1) Role of this module in the reproduction system

`utils/io.py` should be responsible for two separate concerns:

### A. Configuration loading
It must read the provided `config.yaml` and convert it into a structured experiment configuration object or dictionary.

This config object must preserve the hierarchy and values exactly as specified in `config.yaml`, because the reproduction must not invent any values. The module should serve as the single source of truth for:

- experiment seed control
- number of seeds and ensemble settings
- preprocessing policy
- training settings
- tuning search spaces
- model hyperparameter ranges
- baseline settings
- evaluation settings
- implementation constraints

### B. Artifact persistence
It must save and load experiment artifacts in a format that is easy to reuse across the pipeline, including:

- tuned hyperparameters
- validation/test metrics
- predictions
- ensemble outputs
- training logs
- possibly model metadata or checkpoint references

The module must not implement training or evaluation logic itself; it only provides reliable I/O utilities.

---

## 3) Interface responsibilities

The task specifies these public functions:

- `load_config(path)`
- `save_json(obj, path)`
- `save_pickle(obj, path)`
- `load_pickle(path)`

This module must provide these functions exactly.

### 3.1 `load_config(path)`
This function should:

1. Accept a file path to YAML or JSON
2. Parse the file content
3. Return a structured config object

The returned object should be suitable for direct use by the rest of the pipeline. It can be either:
- a nested dictionary, or
- a typed dataclass / pydantic object

Given the design and shared knowledge, a typed object is preferable for consistency, but the implementation must remain lightweight.

#### Logic requirements
- preserve nested structure
- keep numeric values exactly as given in `config.yaml`
- do not infer missing values
- do not apply defaults unless explicitly encoded in the config
- allow access to nested fields in a stable way

#### Recommended behavior
- detect file extension or attempt YAML parsing first, then JSON fallback
- support `.yaml`, `.yml`, and `.json`
- return an `ExperimentConfig`-like object or a nested dict matching the config schema

### 3.2 `save_json(obj, path)`
This function should serialize Python objects to JSON for:
- hyperparameter summaries
- validation/test metrics
- ensemble scores
- experiment metadata

#### Logic requirements
- create parent directories if needed
- convert non-JSON-native objects using a safe serializer
- ensure deterministic formatting if possible
- do not silently lose important numeric precision

### 3.3 `save_pickle(obj, path)`
This function should save arbitrary Python objects, especially:
- trained model metadata
- split objects
- preprocessing objects
- prediction arrays
- Optuna study objects if needed

#### Logic requirements
- create parent directories if needed
- use standard pickle protocol
- be compatible with NumPy arrays, pandas objects, and model-related objects

### 3.4 `load_pickle(path)`
This function should load previously saved pickle artifacts.

#### Logic requirements
- exact inverse of `save_pickle`
- validate path existence before loading
- return the original object

## 4) Data structures and config handling strategy

Although the design allows a dict-like config, the module should aim for a lightweight typed structure to improve reproducibility and reduce accidental key mismatches.

### 4.1 Suggested config representation
Use a dataclass-based object or nested dataclass tree, if implemented cleanly.

At minimum, the loaded config should provide access to:
- `config.experiment.seed`
- `config.training.max_epochs`
- `config.models.transformer.layers.other`
- etc.

If a fully typed nested dataclass tree is too cumbersome, a nested mapping with helper access is acceptable, but it must remain stable and explicit.

### 4.2 Preservation of raw values
The loader should not coerce values beyond what parsing naturally yields.

Examples:
- `5.0e-05` should load as float
- `[1, 16]` should remain a two-element list
- `0.0` should remain float
- `"gbtree"` should remain string

### 4.3 No invented defaults
The config file already specifies:
- seed = 42
- num_seeds = 15
- patience = 16
- max_epochs = 100
- etc.

The module must not invent replacements if a key is missing. Instead:
- either raise a clear error
- or return the loaded data as-is and let downstream modules validate required fields

For reproducibility, the safer choice is to validate required keys and fail early if anything is missing.

## 5) Validation logic that should exist in `load_config`

The configuration file is central to the experiment. The loader should validate the presence of all required top-level sections and key nested paths.

### 5.1 Required top-level sections
Validate that the config contains:
- `experiment`
- `data`
- `training`
- `hyperparameter_tuning`
- `models`
- `evaluation`
- `baselines`

`notes` can be treated as optional metadata, though it is present.

### 5.2 Required consistency checks
The loader should check that:

- `experiment.num_seeds` matches the paper’s 15-seed evaluation protocol
- `experiment.num_ensembles` and `experiment.ensemble_group_size` are consistent
- `training.lr_schedule` is `none`
- `training.early_stopping.patience` is present and matches the config
- `data.preprocessing.numerical.otto_group_product_classification` is `none`
- `evaluation.test_runs_per_tuned_config` equals the number of repeated seed evaluations
- `training.loss.classification` and `training.loss.regression` are both specified
- all dataset batch sizes are present
- transformer-specific dataset group keys (`sa_co_mi`, `other`) exist

These checks ensure the rest of the system can rely on a complete config.

## 6) Serialization requirements for reproducibility

This module is not just for configs; it also supports the experiment lifecycle.

### 6.1 JSON outputs to support
Use JSON for:
- tuned hyperparameters per model-dataset pair
- validation results
- test results
- rank tables
- ensemble metrics
- experiment manifests

These are human-readable and easy to compare between runs.

### 6.2 Pickle outputs to support
Use pickle for:
- cached datasets or processed splits
- preprocessing transformers
- Optuna studies
- prediction arrays if needed
- checkpoint metadata if storing non-torch objects

For actual model weights, PyTorch checkpoint saving may happen elsewhere, but `save_pickle` can still store associated metadata.

## 7) Interaction with the rest of the pipeline

This module must integrate cleanly with all other modules in the design.

### 7.1 `main.py`
`main.py` should call:
- `load_config(config_path)`
- `save_json(...)` for outputs
- `save_pickle(...)` for caches or studies if needed

### 7.2 `utils/reproducibility.py`
Configuration loading happens before:
- `set_seed(config.experiment.seed)`
- `set_deterministic()`

So `load_config()` must return the seed value in a directly accessible location.

### 7.3 `training/tuning.py`
The tuner needs:
- tuning method
- trial count
- search spaces
- model ranges
- dataset-dependent transformer ranges

The config loader must preserve all of these nested structures exactly.

### 7.4 `baselines/gbdt.py`
GBDT baseline code depends on:
- fixed CatBoost/XGBoost settings
- tuning parameter ranges
- dataset-specific GPU/CPU behavior from the paper’s logic

The module should simply expose these settings unchanged.

---

## 8) Path handling requirements

All I/O functions should work robustly across environments.

### 8.1 `pathlib.Path` support
Accept both strings and `Path` objects.

### 8.2 Parent directory creation
For save functions:
- create parent directories automatically if they do not exist

### 8.3 Existence checks
For load functions:
- validate that the file exists
- raise a clear error if not found

### 8.4 Extension handling
`load_config()` should support:
- `.yaml`
- `.yml`
- `.json`

For output functions:
- `save_json` should ensure `.json` output paths are accepted
- `save_pickle` can use any suffix, but `.pkl` or `.pickle` is recommended

---

## 9) Determinism and reproducibility considerations

Although this module does not set seeds itself, it affects reproducibility through deterministic config handling and artifact storage.

### 9.1 Stable config parsing
Repeated loads of the same config file should yield equivalent structures.

### 9.2 Stable serialization
When saving JSON:
- use stable key ordering if possible
- use indentation to make outputs auditable
- avoid nondeterministic formatting

### 9.3 Artifact traceability
Saved outputs should ideally include:
- dataset name
- model name
- seed
- timestamp or run ID if handled externally

If `utils/io.py` does not generate run IDs itself, it should at least support saving to structured paths chosen by `main.py`.

---

## 10) Error handling strategy

The module should fail fast and clearly.

### 10.1 Config parsing errors
If YAML/JSON parsing fails:
- raise a descriptive exception
- include the file path in the error message

### 10.2 Missing key errors
If required config keys are missing:
- raise a clear validation error
- identify which key path is absent

### 10.3 Serialization errors
If a given object cannot be serialized to JSON:
- either convert it safely
- or raise a descriptive error rather than silently truncating data

---

## 11) What this module should not do

To keep the design clean and faithful to the paper:

- do not perform data loading
- do not split datasets
- do not preprocess data
- do not build models
- do not train models
- do not compute metrics
- do not tune hyperparameters

It should only handle:
- config loading/validation
- JSON/pickle persistence

---

## 12) Recommended implementation priorities

Order of implementation for this module:

1. Implement `load_config(path)`
2. Add schema validation for required keys
3. Implement `save_json(obj, path)`
4. Implement `save_pickle(obj, path)`
5. Implement `load_pickle(path)`
6. Add helper functions for path normalization and safe serialization

## 13) Paper alignment summary

This module supports the reproduction of the paper by ensuring:

- the exact `config.yaml` governs experiment behavior
- all hyperparameters and dataset policies match the paper
- tuning/search spaces are read from configuration, not hardcoded
- evaluation settings such as 15 seeds and ensemble grouping are preserved
- all saved outputs are reproducible and traceable

In short, `utils/io.py` is the glue that guarantees the rest of the system follows the paper’s experimental protocol exactly.
